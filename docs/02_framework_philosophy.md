# BRPX 设计思想

> 本文解释当前架构为什么这样组织，以及每项选择解决了什么问题、付出了什么代价。

## 1. 核心哲学

BRPX 的核心原则是：公共解析请求保持低延迟和兼容性，管理、规则、审计等控制能力在本机闭环，并且失败时不拖垮解析主路径。

## 2. 运行配置使用快照

问题：Handler 如果长期借用可变配置，Web 保存时容易和请求线程互相阻塞。

解法：`AppState` 保存 `Arc<RwLock<Arc<BiliConfig>>>`。每次请求快速取得一个 `Arc` 快照，后续异步调用只读该快照；保存时一次替换整个 `Arc`。

```text
request A ----> snapshot A ----------> finish
                       |
Web save ------> replace Arc
                       |
request B ----> snapshot B ----------> finish
```

价值：读锁持有时间短，请求内配置一致。代价：监听端口、Worker、Redis Pool 等启动期对象不能仅靠换快照重建，因此管理 API 会返回 `restart_required`。

## 3. 规则保存在本机

问题：外部黑名单带来隐私、可用性和控制权风险，旧逻辑还把策略散落在配置与远程请求中。

解法：`AccessControlService` 把 UID、精确 IP、CIDR 和令牌指纹统一放入 SQLite，并用固定优先级计算结果：令牌 > UID > 精确 IP > CIDR；同优先级拒绝优先。

价值：规则来源和生效时间可审计，不依赖第三方。代价：运营者需要自己维护规则，并正确配置可信反向代理。

## 4. 审计不阻塞请求

问题：每次请求同步写 SQLite、再查剧集标题，会把磁盘和公网延迟叠加到播放接口。

解法：中间件只构造脱敏事件并 `try_send` 到容量 2048 的队列；Worker 写入 SQLite，剧集标题最多四个并发补全。队列满时丢弃审计而不是阻塞解析。

```text
request -> response
    |
    `-> try_send -> SQLite -> optional metadata fetch
          |
          `-> full: counter + 1
```

价值：主路径延迟可预测。代价：极端过载时审计不是绝对完整，仪表盘必须观察丢弃计数。

SQLite 当前由单个 `Connection` 和进程内 `Mutex` 保护。查询简单，但它们仍是同步操作，会串行争用并占用所在 Actix Worker；增加重查询前应先评估迁移到专用阻塞线程或连接池。

## 5. Redis 与 SQLite 分工

Redis 保存高频、带 TTL、服务兼容所需的数据；SQLite 保存低频但需要筛选和持久化的管理数据。

| 数据 | 存储 | 原因 |
|---|---|---|
| 播放/用户/地区缓存 | Redis | 高频、TTL、已有协议 |
| 管理密码哈希/会话 | SQLite | 持久、事务和唯一键 |
| 本地规则 | SQLite | CRUD、排序、过期查询 |
| 请求审计 | SQLite | 条件筛选与保留期 |

## 6. 管理 UI 嵌入二进制

问题：单独部署 Node 前端会让一键安装增加版本和静态目录管理。

解法：管理页是一个原生 HTML/CSS/JS 文件，Lucide 也本地内嵌，由 Rust 路由返回。

价值：一个二进制即可运行，无 CDN 依赖。代价：UI 代码没有组件编译器，修改时必须依靠浏览器回归测试保持结构清晰。

## 7. 秘密只显示掩码

管理 API 将 Redis URL、token、secret、access key 等字段替换为 `********`；保存时只有仍为掩码的字段才恢复原值。写盘使用临时文件、`sync_all`、备份和重命名。

这相当于让浏览器拿到可编辑的“配置视图”，而不是秘密原文。代价是新增秘密字段必须符合命名规则并补测试。

## 8. 思想汇总

| 思想 | 体现 | 解决的问题 |
|---|---|---|
| 不可变请求快照 | `AppState::config_snapshot()` | 并发配置读取 |
| 控制面本地化 | SQLite + Web 管理 | 外部黑名单依赖 |
| 主路径优先 | 有界审计队列 | 审计拖慢解析 |
| 数据按访问模式分层 | Redis + SQLite | 单一存储不合适 |
| 单二进制交付 | `include_str!` | 安装复杂度 |
| 秘密最小暴露 | 掩码、Argon2、CSRF | 管理端泄密 |

检查新设计时先问：它是否会阻塞公共请求？是否引入新的外部控制点？失败时能否降级且被观察到？
